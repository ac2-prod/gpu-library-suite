# GPU Library Suite Decision Register

## Authority and scope

This document records decision status and rationale only. The linked
specification is authoritative for implementation details; this register does
not duplicate CLI rules, schemas, mathematical formulas, result trees, or
system procedures.

| ID | Status | Decision summary | Rationale | Authoritative specification |
| --- | --- | --- | --- | --- |
| D-001 | Accepted | The repository name is `gpu-library-suite`. | It describes the technical scope without using an unrelated program identity. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-002 | Accepted | Current user instructions take precedence over the 2026-07-13 teaching edition, which takes precedence over older material. | One explicit authority order prevents historical material from silently changing the implementation. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-003 | Accepted | The repository hierarchy is vendor first, then language, library, and purpose. | This is the primary user navigation model. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-004 | Accepted | Teaching examples and performance benchmarks are separate. | Teaching clarity and measurement machinery have incompatible concerns. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md), [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-005 | Accepted | Teaching-example filenames match the 2026-07-13 material. | Printed material and compilable source must correspond exactly. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-006 | Accepted | Initial implementation is limited to NVIDIA C/C++ without empty AMD or Fortran placeholders. | Future scope should not be misrepresented as implemented. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-007 | Accepted | HAIRDESC is not used in repository identifiers, namespaces, executable names, package names, or library names. | This repository is maintained independently and is not an official HAIRDESC repository. | [`AGENTS.md`](../AGENTS.md) |
| D-008 | Accepted | No license is added until the project owner selects one. | Licensing and publication policy remain unresolved owner decisions. | [`AGENTS.md`](../AGENTS.md) |
| D-009 | Accepted | Portable code contains no Pegasus-specific value; initial system-specific artifacts live only under `jobs/pegasus`. | Separation preserves reuse on other supported systems and local GPU servers. | [`AGENTS.md`](../AGENTS.md), [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-010 | Accepted | Initial job support excludes Furo and does not create related directories or scripts. | It is outside the approved initial system scope. | [`AGENTS.md`](../AGENTS.md) |
| D-011 | Accepted | JSON is the configuration format instead of TOML. | Python 3.9 can read JSON without an added package. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-012 | Accepted | Project metadata uses deterministic serialization and rejects duplicate keys, non-standard numeric constants, and invalid UTF-8 on input. | Exact bytes and strict input parsing are required for reproducible hashes and portable JSON. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-013 | Accepted | Repository-owned canonical filenames do not carry manually maintained date or version suffixes. | Git history, tags, releases, and in-document schema versions provide versioning. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-014 | Accepted | `configs/benchmark.json` and `configs/pilot.json` are the canonical production and pilot configuration names. | Stable names prevent competing “latest” configuration files. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-015 | Accepted | Machine-readable schema versions are stored inside documents and change only for incompatible formats. | Format compatibility is distinct from ordinary benchmark-parameter edits. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-016 | Accepted | Upstream-mandated names such as `cublas_v2.h` are preserved. | Repository naming policy must not corrupt external API names. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md) |
| D-017 | Accepted | CUDA and OpenACC use separate CMake build trees. | Their normal C++ compiler toolchains cannot be mixed safely in one configure. | [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-018 | Accepted | Benchmark executables remain single-node and single-process; the launcher provides multi-node repetition. | This keeps portable executables simple while enabling controlled node sampling. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-019 | Accepted | CPU, CUDA, and OpenACC are paired within each wave/hostname block. | Within-block comparison controls node and time effects better than ratios of global medians. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-020 | Accepted | Aggregation is block, then wave, then cross-wave, with wave medians as the sole primary cross-wave input; a flat pool is exploratory only. | Wave is an experimental level and must not disappear or be reweighted by node count in the primary analysis. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-021 | Accepted | Implementation permutation and size order use independent assignments. | Avoiding perfect correlation permits order effects to be distinguished. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-022 | Accepted | Nodes are never automatically excluded because they are slow. | Anomaly flags and visible failures preserve experimental integrity. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-023 | Accepted | CPU backends have explicit production/reference roles, and speedup never falls back to reference automatically. | Correctness fallbacks are not equivalent performance baselines. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-024 | Accepted | The cuSOLVER CPU teaching example uses its one-call teaching API, while the CPU benchmark uses staged factorization and solve. | Benchmark stages must correspond across CPU, CUDA, and OpenACC without rewriting the canonical lesson. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md), [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-025 | Accepted | OpenACC data directives own managed-array allocation/movement; `host_data use_device` only translates addresses. | This prevents double allocation and clarifies CUDA-library interoperability. | [`PROJECT_SPECIFICATION.md`](PROJECT_SPECIFICATION.md), [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-026 | Accepted | Mutable state is restored after warm-up, before every trial, and before every end-to-end repeat where required. | Every independent measurement must begin from the specified canonical state. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-027 | Accepted | Q1/Q3 use Python’s inclusive quartile method with explicit zero/one-sample behavior. | A single reproducible definition avoids tool-dependent summaries. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-028 | Accepted | The PBS job master performs preflight and is the exclusive campaign/wave metadata writer before launching measurement processes. | Out-of-band ownership avoids metadata races without requiring an MPI coordination collective. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-029 | Accepted | Verification evidence and thresholds are objects for every benchmark. | Uniform object shape supports multiple independent metrics without union-type ambiguity. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-030 | Accepted | Executable manifests commit to binary SHA-256 values. | Path and build labels alone do not identify executable content. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-031 | Accepted | Production runs require clean source; dirty smoke/pilot runs require complete source provenance. | Campaign waves must be reproducible and must not mix different source states. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-032 | Accepted | Reproducibility uses effective configuration, immutable run metadata, Git state, source provenance, executable-manifest hash, and binary hashes. | No single identifier captures all inputs to a measurement campaign. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-033 | Accepted | Benchmarks emit machine-readable records, while the suite runner is the sole node raw-result file writer. | One writer can validate output, prevent overwrite, and preserve failures without file races. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-034 | Accepted | Runtime software environment is captured and hashed, and its hash must match across waves in one campaign. | Identical binaries can load materially different drivers and shared libraries. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-035 | Accepted | Measurement and telemetry carry explicit UTC interval timestamps and timezone context. | Interval correlation is required for delayed samples and local-midnight rollover. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-036 | Accepted | Node benchmark failures are isolated for artifact recovery, followed by a job-master completeness decision. | One failure must not destroy other node evidence, but incomplete or failed campaigns must still return failure. | [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
| D-037 | Accepted | A primary campaign has exactly one production CPU backend per benchmark; extra backends are separate or auxiliary. | A unique, explicit denominator prevents ambiguous or automatic speedup selection. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-038 | Accepted | C targets C17; C++, CUDA, and OpenACC C++ target C++17. | Explicit common language levels reduce compiler-dependent behavior across build trees. | [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-039 | Accepted | cuRAND CPU and GPU series compare the same output task and type, not algorithm-equivalent random streams. | The standard-library engine and CUDA generator use different algorithms and interval contracts. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-040 | Accepted | Warm-up, repeat, and trials are configured per benchmark, normalized problem, and scope, with no implementation-local override. | CPU, CUDA, and OpenACC remain comparable while compute and end-to-end timing can use different repetition. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-041 | Accepted | Raw rows distinguish attempted failures from unattempted skipped trials and retain a controlled failure origin. | A crash or fatal predecessor must not falsely describe never-started work as an executed failure. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-042 | Accepted | Pegasus cuFFT speedup uses threaded FFTW as the primary CPU backend; serial FFTW is auxiliary and never an automatic fallback. | A serial teaching-correspondence result is not an equivalent production denominator. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md) |
| D-043 | Accepted | OpenACC CUDA-library targets use CMake CUDA imported targets with the same Toolkit selected by NVHPC; OpenACC Thrust also uses NVHPC CUDA C++ interoperation. | One verified Toolkit and link model avoids ABI/path ambiguity across OpenACC and CUDA libraries. | [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md), [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-044 | Accepted | CMake target/executable names match source stems, and manifest artifacts have content-derived identities plus unique semantic and build keys. | Stable names preserve teaching correspondence while explicit metadata distinguishes providers and build profiles. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-045 | Accepted | C/C++ result serialization fixes the numeric locale, uses round-trip precision, canonicalizes negative zero, and rejects nonfinite JSON numbers. | Machine-readable output must not depend on host locale or emit invalid JSON. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md), [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-046 | Accepted | Pilot and benchmark configuration values begin as explicit calibration candidates in the canonical files and are updated in place after pilot measurement. | Calibration changes are data changes, not schema revisions or reasons to create competing filenames. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-047 | Accepted | Implementation advances through six required phase gates; optional dependency absence is acceptable only when target-disable behavior is correct. | Required failures must be repaired before later work can rely on the affected phase. | [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) |
| D-048 | Accepted | Git metadata availability is explicit; unavailable Git state uses null commit/dirty values and is never treated as clean. | Source archives must produce valid metadata without becoming eligible for production provenance. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-049 | Accepted | CPU role, series, parallelism, and effective-thread metadata come from the configured series or a backend observation, never backend-name heuristics. | Names do not reliably encode execution semantics, and requested threads are not proof of effective threads. | [`BENCHMARK_PROTOCOL.md`](BENCHMARK_PROTOCOL.md), [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-050 | Accepted | Raw and manifest compiler flag metadata is named `global_configure_flags` unless complete target-level effective flags are captured. | Field names must not overstate global CMake flag coverage. | [`RESULT_SCHEMA.md`](RESULT_SCHEMA.md) |
| D-051 | Accepted | Pegasus runtime does not require compiler commands by default, and GPU identity is collected independently on every node. | Prebuilt binaries need runtime libraries and node-local device provenance, not a compiler installation or another node's identity. | [`PEGASUS_EXECUTION.md`](PEGASUS_EXECUTION.md) |
